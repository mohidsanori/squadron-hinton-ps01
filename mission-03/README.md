AURA's attention mesh chokes on long sensor streams: naive attention is quadratic in context length, and the KV-cache saturates memory bandwidth. This mission rebuilds the transformer attention pipeline from first principles in PyTorch and audits its memory limits:

- **Attention core** — multi-head self-attention with causal masking and a variance-preservation test for the $1/\sqrt{d_k}$ scale.
- **Positions** — Rotary Position Embeddings, proof and test of relative-distance invariance, decay compared with ALiBi.
- **Memory** — Grouped-Query Attention and an autoregressive KV-cache, benchmarked for MHA, GQA 4:1 and MQA up to 32k tokens.
- **Safety** — FlashAttention IO derivation, a KV-cache denial-of-service simulation, and PagedAttention / MLA as defences.

| Script | Checks (all pass) |
|---|---|

| 02 | `apply_rope` equals the explicit rotation matrix $R^d_{\Theta,m}$; norms preserved; ⟨RoPE(q,m), RoPE(k,n)⟩ = g(q,k,m−n) for 1,000 random shifts; RoPE vs ALiBi decay plot; context extrapolation (plain vs position interpolation vs NTK) |
| 03 | GQA with H_KV = H_Q equals Part 1's MHA exactly; grouped broadcast equals `repeat_interleave`; cached token-by-token decoding equals a full causal pass (MHA, GQA, MQA); cache overflow is rejected; benchmark |

## Key results

**KV-cache benchmark** (LLaMA-3-8B shape, fp16, batch 1; full table with latencies in [`03_benchmark_results.md`](03_benchmark_results.md)):

| N | MHA 32:32 | GQA 32:8 | MQA 32:1 | Traffic @ 50 tok/s, MHA → GQA |
|---:|---:|---:|---:|---:|
| 1,024 | 0.50 GiB | 0.12 GiB | 0.02 GiB | 26.8 → 6.7 GB/s |
| 4,096 | 2.00 GiB | 0.50 GiB | 0.06 GiB | 107.4 → 26.8 GB/s |
| 16,384 | 8.00 GiB | 2.00 GiB | 0.25 GiB | 429.5 → 107.4 GB/s |
| 32,768 | 16.00 GiB | 4.00 GiB | 0.50 GiB | 859.0 → 214.7 GB/s |

- At 32k tokens the MHA cache (16 GiB) is larger than the model's weights. GQA saves 75%, MQA 96.9%.
- Measured decode step at 32k (one layer, laptop CPU, varies between runs): MHA 90 ms, GQA 42 ms, MQA 27 ms. GQA is about 2× faster than MHA in every run.
- The KV-cache made a decoding step over 500× faster than recomputing the sequence at N = 2048.
- **Side quest:** SRAM tiling cuts simulated HBM traffic 3.9× at N = 4096 (7.4× with causal block skipping). Target was 3×.
- **DoS:** on an 80 GB H100, 7 max-length (64k) GQA sessions cause a CUDA OOM; with MHA, 2 do. PagedAttention prevents the crash but a single rogue client still starves the crew (47% of turns served). Paging plus per-client quotas restores 100%.

## Notes on the briefing

- The briefing says the KV-cache gives "O(1) token generation". A cached step is O(N), because it still reads all N cached keys and values; total generation drops from O(N³) to O(N²). The scripts and notebook say this explicitly.
- "HBM traffic from O(N²) to O(N)" is true of FlashAttention's **memory footprint**. Its IO is Θ(N²d²/M): still quadratic, but divided by M/d². The audit derives both.
- The audit template lists ~50 MB of SRAM per SM; an H100 has up to 228 KB per SM. Corrected in audit §1.1.
- The site's Part 5 mentions testing attention parameters "on the portal simulator". We could not find one on the site, so the notebook's last section has a parameter explorer instead.
